# Формат памяти

SQLite — источник истины. Markdown планы, ТЗ и статьи — человекочитаемые результаты, связанные с задачами через пути файлов. В новой сессии состояние восстанавливается из базы. Для переноса между компьютерами или проектами перенеси базу и связанные файлы; память не синхронизируется автоматически.

`show` возвращает оболочку `{site, version, state}`. Для записи создай JSON файл **только объекта state**, сохранив все существующие поля. Затем:

```sh
python3 <skill>/scripts/memory.py --db <project>/.seo/memory.sqlite3 save example.com --file <state.json> --expected-version 1 --note 'Исследованы конкуренты, добавлены первые темы'
python3 <skill>/scripts/memory.py --db <project>/.seo/memory.sqlite3 history example.com
```

Укажи фактическую версию последнего чтения. После успешной записи версия увеличивается. После конфликта перечитай состояние и внеси свои изменения в актуальную версию. При ошибке валидации запись целиком откатывается. Не удаляй и не перенумеровывай задачи. Для исправления прошлого добавляй объяснение в `decisions`. Снимки предыдущих состояний остаются в таблице `events`; `history` показывает их версии, даты и причины.

## Состояние schema_version=1

- `profile` (объект): обязательный `site` из CLI, исходный URL, продукт, аудитория, регион, языки, поисковые системы, бизнес цель, ресурсы, темп публикаций, допущения, путь к плану. URL пути не меняют ключ сайта.
- `research` (массив, только дополнение): записи с `id`, `checked_at`, `source_url`, `query`, `engine`, `market`, `finding`, `confidence`, `limitations`. Для пользовательских данных вместо URL укажи путь файла или источник сообщения. Ссылки на записи используй в задачах.
- `pages` (массив): актуальный инвентарь с URL, заголовком, интентом, кластером, языком, датой проверки, известным статусом индексации и источником этого знания. Неизвестное обозначай `null`.
- `tasks` (массив): задачи со стабильными ID вида `SEO-001`. Минимум `id`, `title`, `status`. Остальные поля по смыслу: `kind` (research/content/technical/measurement), `action`, `cluster`, `intent`, `primary_query`, `secondary_queries`, `language`, `market`, `target_url`, `priority`, `priority_reason`, `evidence_ids`, `depends_on`, `effort`, `scheduled_for`, `brief_path`, `draft_path`, `published_url`, `published_at`, `completion_evidence`, `blocker`, `review_after`, `updated_at`.
- `decisions` (массив, только дополнение): дата, решение, причина и затронутые ID. Включай изменения допущений, отмену, перенос, исправления и возобновление завершённых задач.
- `metrics` (массив, только дополнение): дата получения, источник, URL/запрос/сайт, начало и конец периода, рынок, поисковик, устройство при наличии, измеренные значения и ограничения сравнения. Отсутствующее — `null`, а не ноль.

Поля задач расширяемы. Для написания статьи используй `editorial_path` и `editorial_verdict` в дополнение к `draft_path`. Для аудита: `finding_key` (устойчивый ключ проблемы и URL/шаблона), `audit_path`, `acceptance_criteria`, `confidence`, `verification_state` и `last_checked_at`. `verification_state` — отдельное поле наблюдения, а не замена статусу задачи. При повторном аудите сопоставляй задачи по ключу проблемы и охвату; не создавай дубликаты. Доказательство исправления обязательно для `done`.

Сам скрипт проверяет базовую структуру, ID, зависимости, конфликты версий и подтверждение завершения. Качество SEO данных и источников проверяет агент.

## Статусы

`backlog` → `planned` → `in_progress` → `draft` → `published` → `measuring` → `done` — обычный путь контентной задачи. Исследование или техническая задача может перейти из `in_progress` сразу в `done` с подтверждением результата. Это ориентир, а не обязательный автомат переходов. `blocked` требует описания препятствия, `cancelled` — причины в решениях. Возобновление допустимо с объяснением.

`published` и `measuring` требуют `published_url`; `done` требует `completion_evidence`. Не закрывай задачу только потому, что она добавлена в план. Для статьи можно считать задачу завершённой после подтверждённой публикации, если измерение выделено в отдельную связанную задачу. Это не утверждение роста трафика.

Внешние действия и локальное сохранение не образуют общую транзакцию: если публикация состоялась, а сохранение упало, сначала проверь CMS/URL и восстанови запись, не публикуй повторно.
